## P6-06 backup package

- Added `deploy/kubernetes/backup/` with a daily CronJob and the atomic custom-format backup/rotation script packaged in the dedicated backup image. The job uses UID/GID 70, a dedicated PVC reference, encrypted-secret key references, no service-account token, and seven-daily/four-weekly retention. Its `02:00` schedule explicitly sets `timeZone: Etc/UTC`, matching the backup script’s UTC identifiers and freshness metrics independent of the controller host timezone. It has not been applied. The CronJob now references the derived backup image as a published-digest placeholder; the local image removes the upstream unused `gosu` binary and scanned with zero HIGH/CRITICAL findings. Publish that image from validated `main`, scan the published digest, and produce its SPDX SBOM before promotion.
- Corrected the backup PVC sizing method: weekly archives are hard links to daily archive files, so their data blocks are not counted twice. Sizing must use representative compressed archive measurements and account for up to eleven retained archive paths by unique file, a concurrent in-progress dump before pruning, filesystem/metadata overhead, observed growth over the retention window, and an explicit reserve. No PVC request is assigned until Longhorn capacity and a production-like backup are measured.
- Added a nonblocking kernel `flock` before any shared backup state/metrics/retention access. The scheduled CronJob and wave-1 pre-migration hook share the same PVC; a restricted contender exited with `already_running`, and after killing its holder a real local PostgreSQL backup succeeded. This prevents the separate Job from racing the CronJob but does not substitute for validating the actual production volume and live sync behavior.
- Local Docker used real PostgreSQL with three disposable users and finance rows. Eight successful dumps rotated to seven dailies; checksums and `pg_restore --list` passed; weekly pruning kept four and a UTC-week snapshot hard-linked to its daily archive. An isolated restore returned 3 users, 7 transactions, 10 journals, 21 postings, and 9 revisions. A forced connection failure left all seven known-good daily snapshots and their last-success timestamp intact while recording run success as 0. A fresh restricted-runtime check then ran the built image as UID 70 with a read-only root filesystem, all capabilities dropped, and `no-new-privileges`: the success archive passed `pg_restore --list`; a forced DNS/database failure set latest-run success to 0 while retaining the prior success timestamp and archive.
- Production remains gated on measured PVC capacity, actual namespace/network/service conventions, encrypted Secret creation, textfile exporter wiring, Kustomize/Kubernetes version validation, and an isolated restore drill on the selected production volume.
