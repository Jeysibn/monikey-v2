# Release flow

The V2 repository follows the approved `feature → dev → main` workflow.

1. Create a short-lived `feature/<scope>` or `fix/<scope>` branch from `dev`.
2. Open a pull request into `dev`. `validate`, `CodeQL`, and `e2e` must pass; resolve all review conversations. The E2E check includes fresh PostgreSQL migrations, schema constraints, all API integration suites, and real-stack Playwright.
3. After an integrated milestone is accepted on `dev`, open a pull request from `dev` to `main` with evidence and release notes.
4. Merge only when the same required checks pass. The repo owner is the only current reviewer, so required approval count is zero; pull requests and status checks remain mandatory.
5. After the `dev`→`main` PR is merged, the owner may manually dispatch the image-publication job from `main` with `publish_images=true`. The release job verifies the associated merged PR and successful `validate`, `e2e`, and `CodeQL` checks before building, scanning, and publishing images. It does not rerun PR validation. After all six immutable images are scanned and their SBOMs are generated, a local release-manifest guard verifies the source SHA, latest Prisma migration directory, PR number/head against the earlier verifier outputs, exact image set, canonical GHCR repositories, and immutable SHA-256 digests before the artifact is accepted as complete.
6. Review the uploaded digest map, Trivy JSON reports, and SPDX SBOMs; verify GHCR package visibility; then render a candidate from the verified release manifest with `npm run render:release-manifests`. Set `RELEASE_MANIFEST`, `GITHUB_REPOSITORY`, `GITHUB_SHA`, `VALIDATED_PR`, `VALIDATED_PR_HEAD`, `KUSTOMIZE_BIN`, and a new `RENDERED_MANIFEST_OUTPUT` path outside all Git checkouts. The renderer requires a clean checkout at the source commit, verifies the PR, migration schema version, and all six digests, then writes a Kustomize-rendered candidate with every workload image pinned. Review that candidate and prepare a separate GitOps PR; do not copy it directly into a live checkout without review. The cutover Ingress remains a separately reviewed resource because V1 currently owns the hostname. Merging to `main` or publishing images does not deploy production.

`main` is the default branch. Both `main` and `dev` require pull requests, strict current `validate`, `CodeQL`, and `e2e` checks, resolved conversations, and prohibit force pushes and branch deletion. GitHub API verification on 2026-10-23 confirmed these settings on both branches; required approval count is zero because the owner is the only reviewer. The manual image-publication job is in the existing workflow, is gated to `main` and explicit opt-in, and does not change the homelab GitOps repository.

PR validation runs once for each pull request targeting `dev` or `main`. The workflow has no branch-push trigger because protected branch policy requires all changes to arrive through pull requests; this avoids running the same validation once for the branch push and again for the pull request. A manual image-publication dispatch runs only the release job; the PR test jobs are skipped.
